# DeepChat Persistence / History — Implementation Study (for TBAi)

> Audit-only study. No DeepChat code was copied. Conclusions are based on the actual
> DeepChat source at `D:\Temp\deepchat` (version `1.1.2-beta.3`, Electron app).
> File paths and symbols are cited so the study can be audited.

## 1. DeepChat implementation overview

DeepChat is an **Electron** app. The architecture that matters for persistence is a
strict **process split**:

- **Renderer (UI, Vue 3 + Pinia + shadcn/vue)** never touches the database.
- **Main process (Node, Bun-style tooling)** owns a **synchronous SQLite** database
  (`better-sqlite3-multiple-ciphers`) and exposes it to the UI through a **typed IPC
  bridge** (`@shared/contracts/routes` + `DeepchatBridge.invoke`).
- The UI talks to persistence only via `SessionClient` (`src/renderer/api/SessionClient.ts`),
  which wraps bridge routes: `sessionsCreateRoute`, `sessionsListRoute`,
  `sessionsRenameRoute`, `sessionsDeleteRoute`, `sessionsForkRoute`,
  `sessionsSearchHistoryRoute`, `sessionsListMessagesPageRoute`, etc.

The persistence layer is large and has **two overlapping schemas**: a classic
`conversations` / `messages` pair (`src/main/session/data/tables/`) and a newer
"tape/agent" schema (`deepchatSessions`, `deepchatMessages`, `deepchatAssistantBlocks`,
…) plus compaction, ACP, traces, and usage stats. For TBAi only the **classic pair** is
relevant; the tape/agent surface is out of scope.

## 2. Conversation data model

Source: `src/main/session/data/tables/conversations.ts` (`ConversationsTable`) and
`src/shared/types/session.ts` (`CONVERSATION`, `CONVERSATION_SETTINGS`).

**Identification**
- Primary key: `conv_id TEXT` generated by `nanoid()` (not an integer sequence).
- The UI refers to conversations as "sessions".

**Title / name generation**
- `conversationsTable.create(title, settings)` and `rename(conversationId, title)` exist.
- An `is_new INTEGER` column marks whether the title is still the default
  (`rename()` sets `is_new = 0`).
- Title provenance (LLM auto-title vs. first-message-derived) was **not conclusively
  traced** in this study — see Open Questions. The model clearly supports both
  user-renamed and default titles.

**Per-conversation settings stored inline** (`CONVERSATION_SETTINGS`):
`systemPrompt`, `temperature`, `contextLength`, `maxTokens`, `providerId`, `modelId`,
`artifacts`, `enabledMcpTools`, `thinkingBudget`, `reasoningEffort`, `verbosity`,
`enableSearch`/`forcedSearch`/`searchStrategy`, `activeSkills`, `agentWorkspacePath`, etc.
→ **Provider/model is a per-conversation property**, not global.

**Timestamps & ordering**
- `created_at INTEGER`, `updated_at INTEGER` (ms epoch). The list view orders by
  `updated_at DESC` and an index `idx_conversations_updated` supports it.

**Branching / forking**
- `parent_conversation_id`, `parent_message_id`, `parent_selection` columns + indexes.
- `ConversationsTable.listByParentConversationId` / `listByParentMessageIds` support
  branching. `SessionClient.forkSession()` exposes it.

**Attachments / references**
- Separate `messageAttachments` table (`src/main/session/data/tables/messageAttachments.ts`);
  user-message files/links tracked in `deepchatUserMessageFiles` / `deepchatUserMessageLinks`.
  Not part of the core message row.

## 3. Message data model

Source: `src/main/session/data/tables/messages.ts` (`MessagesTable`) and
`src/shared/types/session.ts` (`SQLITE_MESSAGE`, `MESSAGE`, `MESSAGE_METADATA`).

Columns:
- `msg_id TEXT` (`nanoid`), `conversation_id TEXT` with
  `FOREIGN KEY ... REFERENCES conversations(conv_id) ON DELETE CASCADE`.
- `parent_id TEXT` — used for **regeneration variants**.
- `role TEXT` constrained by `CHECK(role IN ('user','assistant','system','function'))`.
- `content TEXT` — **JSON-serialized message blocks** (assistant messages are an array of
  `AssistantMessageBlock`; see `src/shared/chat/messageBlocks.ts`).
- `created_at INTEGER`, `order_seq INTEGER` — ordering is by `created_at, order_seq`
  (index `idx_messages_session`).
- `status TEXT` `CHECK(status IN ('sent','pending','error'))`.
- `metadata TEXT` — JSON `MESSAGE_METADATA` (token counts, timings, model, provider,
  reasoning timings).
- `is_context_edge INTEGER`, `is_variant INTEGER` — context-window edge + regeneration flag.

**Regeneration / variants**
- `getVariants(parentId)`, `getMainMessageByParentId()` return an assistant message with a
  `variants: SQLITE_MESSAGE[]` array. `is_variant = 1` rows are children of the main
  message (keyed by `parent_id`).
- `query()` loads non-variant messages and attaches each assistant message's variants.

**Serialization format**
- Messages are stored as **JSON text**, not normalized columns. Assistant content is an
  array of typed blocks. `clientMessageProjection.ts` strips `providerReplayJson` from
  blocks before sending to the renderer (a privacy/redaction step).

## 4. Persistence layer

**Technology**
- `better-sqlite3-multiple-ciphers` (synchronous SQLite, optional encryption).
  **Not Drizzle** — DeepChat hand-rolls its data layer.
- Abstraction: `BaseTable` (`src/data/baseTable`) with a **manual versioned migration
  system**: `getCreateTableSQLForVersion(version)`, `getMigrationSQL(version)`, and
  `getLatestVersion()` (conversations are at **v10**). Migrations are additive
  `ALTER TABLE … ADD COLUMN` statements.
- `SessionDatabase` (`src/main/session/data/database.ts`) is a facade exposing typed
  table accessors and high-level methods (`createConversation`, `getConversation`,
  `getConversationList`, `queryMessages`, `renameConversation`, `deleteConversation`, …).

**Writes / updates / deletes**
- `insert()` adds a message (status usually starts `pending`, updated to `sent` on
  completion). `update()` only sets the fields provided (partial update).
- Conversation `update()` is also partial — only provided settings columns are written.
- `delete()` on a conversation cascades to its messages (FK `ON DELETE CASCADE`).

**Loads**
- `getConversationList(page, pageSize)` → paginated, `ORDER BY updated_at DESC`,
  returns `{ total, list }`.
- `MessagesTable.query(conversationId)` → full ordered message list with variants.
- `listMessagesPage()` supports cursor pagination in the renderer.

**Migration / versioning**
- Versioned `BaseTable` per table; `databaseStartupRecovery.ts` / `databaseInitializer.ts`
  diagnose and repair schema drift (`DatabaseSchemaDiagnosis`).

## 5. History UI behavior

Source: `src/renderer/src/components/WindowSideBar.vue`, `WindowSideBarSessionItem.vue`,
`src/renderer/src/stores/ui/session.ts` (Pinia `useSessionStore`), `sidebar.ts` (only
collapse state).

- **Structure**: a left agent-rail + a session column. Sessions are grouped: a
  **Pinned** section, a **Chat** section, and **Workspace/Project groups** (group-by
  date or project, toggleable via `sessionStore.toggleGroupMode()`). Groups are
  drag-reorderable (`vuedraggable`).
- **Sorting**: primarily `updated_at DESC`; pinned sessions float to a dedicated section.
- **Search**: a search input filters the list; `SessionClient.searchHistory()` hits the
  main process (`sessionsSearchHistoryRoute`). (Note: `src/renderer/src/lib/searchHistory.ts`
  is a **misnomer** — it is composer *input* history for up/down arrows, not conversation
  search.)
- **New conversation**: `handleNewChat` → `sessionStore.startNewConversation()` →
  `SessionClient.create()`.
- **Open / restore**: `handleSessionClick` → `sessionStore.selectSession(id)` → loads
  messages. Active session highlighted via `sessionStore.activeSessionId`.
- **Rename**: `renameSession()` (dialog/inline).
- **Delete**: `openDeleteDialog` → confirm `Dialog` → `sessionStore.deleteSession()`.
- **Pin**: `handleTogglePin` → `toggleSessionPinned()`.
- **Empty / loading / error states**:
  - Loading first page → skeleton rows (`window-sidebar-loading-first-page`).
  - Empty → `DcEmpty` with title/description (search vs. no-conversations variants).
  - Pagination error → inline error + retry (`sidebar-session-pagination-retry`).
  - Infinite scroll → `handleSessionListScroll` → `sessionStore.loadNextPage()`.

## 6. State flow (user action → restoration)

Example: send a message, then reload and reopen.

1. **User types & sends** → assistant-ui-style composer → `SessionClient`/`ChatClient`
   issues the request; the main process streams assistant blocks.
2. **Streaming → UI state**: `bindMessageStoreIpc` (`src/renderer/src/stores/ui/messageIpc.ts`)
   subscribes to `chatClient.onStreamUpdated/Completed/Failed`. It applies blocks to a
   **streaming state** in the message store and enforces **generation ordering**
   (`acceptStreamUpdate` tracks request generations so stale streams don't overwrite).
3. **Settle → persist**: on `onStreamCompleted`, `settleStream()` invalidates the sidebar
   view and reloads persisted messages (`loadMessages`) so the mounted node swaps to its
   persisted copy without a remount.
4. **Persistence layer**: main process writes the assistant message (`MessagesTable.insert`
   then `update` to `sent` with `metadata`); `updated_at` bumps the conversation.
5. **Reload**: on app restart, the sidebar `useSessionStore` loads
   `getConversationList()`; opening a session calls `queryMessages()` and the renderer
   rehydrates the thread from the DB rows (after `clientMessageProjection` redaction).
6. **Restoration**: the conversation list + selected thread are rebuilt from SQLite.

**Library vs. custom**
- *Library*: SQLite driver, Vue/Pinia reactivity, shadcn/vue components, the IPC bridge
  scaffolding.
- *Custom*: the entire data-layer abstraction (`BaseTable`, versioned migrations),
  the block serialization format, the streaming-generation reconciliation
  (`messageIpc.ts`), the grouping/pagination/composer-input-history logic, and the
  large tape/agent/compaction/ACP subsystems.

## 7. TBAi comparison

| Aspect | DeepChat | TBAi (current) | Implication |
|---|---|---|---|
| App model | Electron (main/renderer, IPC) | Web (React + Vite) ↔ Hono/Bun HTTP | TBAi's equivalent of DeepChat's "main owns DB" is the **Hono backend**; the HTTP API already exists (`/api/conversations`). No IPC needed. |
| DB | `better-sqlite3-multiple-ciphers` + custom `BaseTable`/v10 migrations | `bun:sqlite` (Drizzle removed in cleanup) | TBAi can keep `bun:sqlite` and add a **small messages table**; do **not** copy DeepChat's hand-rolled migration framework. |
| Chat UI / state | Custom Vue thread + block model | `@assistant-ui/react` + AI SDK v7 | assistant-ui already owns message state & rendering. **No custom message store/rendering.** |
| Streaming | Custom generation reconciliation (`messageIpc.ts`) | `AssistantChatTransport` + AI SDK stream | Use the library transport; persist **after** the stream settles. |
| Conversation settings | Per-conversation provider/model/temp inline | Active provider from registry | Minimal TBAi can store `providerId`/`model` per conversation or keep using the active provider. |
| History UI | Very rich (groups, pin, drag, search, archive) | Simple sidebar list | TBAi needs only: list, new, open, (optional) rename/delete. |

## 8. Recommended minimal TBAi design

**Backend (Hono + bun:sqlite)**
- Add a `messages` table mirroring the minimal needed fields:
  `id TEXT PK`, `conversation_id TEXT FK→conversations(id) ON DELETE CASCADE`,
  `role TEXT`, `parts TEXT` (JSON of assistant-ui `parts`), `created_at INTEGER`,
  `order_seq INTEGER`, `status TEXT`.
  (No need for `parent_id`/`is_variant`/`metadata` columns initially.)
- Extend `/api/conversations` with message persistence:
  `GET /api/conversations/:id/messages`, `POST /api/conversations/:id/messages`
  (save the assistant-ui `UIMessage[]` after a turn completes). Reuse the existing
  Zod validation approach.
- Keep conversations table storing `title` + `providerId`/`model` (optional) + timestamps.

**Frontend (React + assistant-ui + Zustand)**
- `useConversationsStore` (already exists) gains `loadMessages(id)` / `saveMessages(id, msgs)`.
- On stream **settle** (assistant-ui `Thread` provides message state), persist the full
  message list for the active conversation via the API — the same "settle then persist"
  idea as DeepChat, but with **zero custom streaming reconciliation** because
  assistant-ui manages it.
- History UI: a config-driven sidebar list (reuse the new `web/src/config/navigation.ts`
  pattern if a history section is added) showing conversations, with New / Open / optional
  Rename / Delete. No grouping/pinning/drag needed initially.

**What to copy vs. not**
- ✅ Copy the *pattern*: backend owns persistence; frontend calls a typed API; persist on
  stream settle; store messages as JSON (`parts`); per-conversation title + timestamps.
- ❌ Do **not** copy: the `BaseTable`/v10 migration framework, block serialization,
  `messageIpc` generation reconciliation, branching/variants, tape/agent/ACP/compaction,
  encryption, grouping/pinning/drag/archive UI.

## 10. Things deliberately excluded

- All "tape", agent-runtime, ACP, compaction, message-trace, and usage-dashboard tables.
- The block-based message content model (TBAi stores assistant-ui `parts` JSON directly).
- Conversation branching/forking and regeneration variants.
- Pinned/grouped/drag-reorderable/archive workspace UI.
- Encrypted SQLite and the custom `BaseTable` migration engine.
- Composer input-history (the misnamed `searchHistory.ts`) — not conversation history.

## 11. Open questions

1. **Title generation**: DeepChat's auto-title source (LLM vs. first-message text) was not
   conclusively located. TBAi can start with a default `"New Conversation"` and add
   optional rename / later LLM auto-title.
2. **Per-conversation provider/model**: Should TBAi store `providerId`/`model` per
   conversation, or always use the active provider? Minimal design can use the active
   provider and add per-conversation override later.
3. **Persistence granularity**: Save the whole message array on settle (simple, idempotent)
   vs. incremental inserts. Whole-array save is recommended for minimal complexity.
4. **`bun:sqlite` vs Drizzle**: TBAi currently uses `bun:sqlite` directly (Drizzle was
   removed during cleanup). Either is acceptable; the study recommends keeping the current
   `bun:sqlite` approach to avoid re-adding a dependency.

## Concise recommendation (smallest TBAi implementation)

Implement conversation history with the **least** custom code by reusing what TBAi already
has:

1. **Backend**: add one `messages` table (`id, conversation_id FK, role, parts JSON,
   created_at, order_seq, status`) and two endpoints —
   `GET /api/conversations/:id/messages` and `POST /api/conversations/:id/messages`
   (validated with Zod, same style as today). Add `title` + `updated_at` handling to the
   existing conversations table/API.
2. **Frontend**: extend `useConversationsStore` with load/save; on assistant-ui thread
   **settle**, POST the message list. Render history as a simple sidebar list (New / Open /
   optional Rename / Delete) — no grouping, pinning, or drag.
3. **Do not** adopt DeepChat's `BaseTable` migrations, block model, IPC, branching,
   agents, or encryption. Those are Electron/agent-platform concerns irrelevant to TBAi.

Estimated custom surface: ~1 SQL table, ~2 Hono routes, ~1 Zustand store extension, ~1
small sidebar list component. Everything else is provided by assistant-ui + AI SDK v7 +
Hono + bun:sqlite.
