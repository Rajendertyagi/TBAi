Asking a question

rebuilt

The question used to be a dead end. Now it is a small panel above the text box that asks one thing at a time.

What was wrong, and why it is not your fault.

The message in the chat showed your three options as a list of words. They looked selectable. They were not â€” that card has never had anything to click on. Underneath it sat a separate box where you actually answered, with no heading and no marker, so most people never found it. You were shown options and then given nowhere to use them.

There was also a needless extra click. The app asked permission to let the agent ask you a question, before showing the question. Asking a question cannot break anything, so there was nothing to approve.

What it does now

  • One question at a time. A three-question form no longer becomes a tall block. It shows 1 of 3, and the dots let you jump to any of them.
  • Your options, clickable. Each is a row, with the reason for it underneath â€” the same wording the agent sent.
  • Still your own answer. Other… opens a box that grows as you type. It only appears when the question allows it, because the server rejects answers that were not on the list.
  • No permission click first. Asking you a question is now allowed automatically. Running a command still asks, exactly as before.
  • Enter moves on, and it understands typing in Japanese, Chinese or Korean â€” pressing Enter to accept a word will not send a half-typed answer.
  • Several questions? They queue. The panel says how many are waiting.

The same card, in its three states

The card had a fourth state it should never have had: a settled question still telling you to go and answer it. Cancelling walked straight into it — the question was gone, and the card said go to the box. It now has three states, and only a question that is genuinely still waiting points anywhere.

Taking the question with you

Sometimes the answer belongs somewhere else â€” a script, another agent, a colleague. There are now two buttons in the top right of the question box, so you can carry it off rather than retyping it.

Tool results that were silently empty

fixed

The worst class of bug in this app: the tool did the work, the answer was real, and the card still said No output. You only saw the result because the model repeated it in prose.

Search & file results â€” before

  • grep â€” a search that found 12 matches showed No output.
  • read â€” the file was read; the card said No output.
  • web search â€” Read 0 sources over an empty band, then the model stated a version number with nothing on screen supporting it.

Two separate causes. First, results were unpacked into plain text, and the code that reads them only understood the packed form â€” so the text was thrown away. One shared change, not a per-tool patch: the code that reads a tool's result now understands every shape the app can hand it, so results survive being unpacked. That repaired grep, read, glob, webfetch, write, task, skill and question at once.

You said this one was ok, not great. The reason is visible below: the card used to have no height limit at all, so a question with a dozen options grew until it pushed the conversation off screen. It now grows to fit its content and stops — it is capped, never given a fixed height.

What the reference app does

answered by the code — we match it

This was left open as a three-way question. It does not need a decision: the reference app already answers it in code, and the rule is worth copying rather than choosing.

It shrinks to fit, with a floor. The body is never given a fixed height. It grows with its content and is only ever capped.

// D:\Temp\openchamber — FormDock.tsx + useMobileAutocompleteMaxHeight.ts
available = max(0, floor(body.bottom − boundaryTop − 8))
next = available < 320 ? max(120, available) : undefined
maxHeight = next === undefined ? undefined : max(120, next − 96)
class = max-h-[50vh] overflow-y-auto overscroll-contain
  • 320 — half the viewport, as a pixel fallback for when half the viewport genuinely does not fit.
  • 120 — the floor, applied twice. A keyboard pan must never collapse the question out of existence.
  • 96 — the chrome the scroll body does not own: title, progress and dots above it, the button row below it. This one I left out of the first port, which would have let a long option list push the title off screen.

So the answer to “shrink or fixed?” is the third option: shrink to fit, with a minimum. Which is what the three drawings above show, and what now ships.

This is the same question still sitting unanswered under Terminal output. It is really one question about the whole family of cards:

  • Shrink to fit — a two-option card is short, a twelve-option card is tall. Quiet, but cards in a column end up different heights and the transcript looks ragged.
  • Fixed height — every card is the same size. Calm and scannable, but a two-option question sits in a box built for twelve and looks padded and empty.
  • Shrink, with a minimum — grows with content, but never shorter than a couple of rows, so a one-line card is not a sliver. This is what ships today, and what the three drawings above show.

The answer changes terminal output, diffs and tool results too, which is why it is worth deciding once rather than per card.
