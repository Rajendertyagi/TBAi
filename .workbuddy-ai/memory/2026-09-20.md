# 2026-09-20 — TBAi work log

## Application-wide observability: operationId + frontend log transport

Extends the existing logger foundation (no new subsystem, no EventBus, no
second store). Baseline checkpoint `83cd9ca1` untouched.

### Correlation
- `operationId` — ONE user action, minted by the FRONTEND, propagated on
  `X-TBAI-Operation-ID`, bound into the backend `RequestContext`/ALS. requestId
  stays request-scoped; both are kept. Backend resolves it via the new pure
  `resolveInboundCorrelation(headers)` in `src/lib/logger.ts` (so the header
  contract is unit-testable without booting the server).
- `RequestContext` gained operationId/threadId/clientRequestId/streamId/sessionId
  (conversationId was declared but never bound; now bound via `logger.child` in
  the chat route, and the tool funnel binds conversationId alongside toolCallId).
- `emit()` now inherits from one `CORRELATION_KEYS` list — the old hand-written
  merge could silently forget a new field.
- Frontend: `web/src/lib/operation.ts` (pure, no logger import — logger →
  transport → operation is the dependency direction). `installOperationHeaderFetch()`
  wraps `fetch` ONCE for same-origin `/api/*` only; the decision lives in the
  pure `operationInitFor`/`isCorrelatableRequest` so tests need no global stub.

### Frontend → backend pipeline
- New `POST /api/logs/client` (in the existing logs module, no new API surface
  family): Zod-validated, byte-capped, flat-scalars-only fields, scope registry
  enforced against the CLIENT subset (a browser cannot inject into `scheduler`).
- `web/src/lib/log-transport.ts`: bounded (200 queue / 20 batch), batched,
  fire-and-forget, drops-on-failure (never retries → no error loop), backoff,
  `pagehide` best-effort flush. Delivery is injectable
  (`setTransportFetchForTests`) so tests never replace global `fetch`.
- Frontend logger has TWO levels: console (dev debug / prod warn, unchanged) and
  transport (dev debug / prod **info**) — production keeps lifecycle evidence
  without turning on debug chatter.
- Browser lines carry `plane: "client"`, `clientTs` (client clock) vs `ts`
  (server receipt). The ingest does NOT inherit the POST's operationId — a
  queued batch can span operations, so each event carries its own or none.

### Loss visibility (was the biggest reliability hole)
- Four counters: `levelFiltered`, `ringSpliced`, `fileQueueDropped`,
  `ioFailures`. Exposed via `GET /api/logs/files → writer.loss` and `/metrics`
  (`tbai_log_entries_*`, `tbai_log_file_io_failures`).
- Ring cap and file-queue cap are now configurable (`TBAI_LOG_RING`,
  `TBAI_LOG_QUEUE`) — both were hardcoded consts, which also made the loss paths
  untestable without flooding the console.
- `shouldSample`/`resetSampleCounters` **removed**: deterministic sampling drops
  evidence silently, the opposite of what reconstruction needs. Its tests were
  removed with it (not weakened).
- Entries gained `ts` (epoch ms); `time` stays the human string. Console skips
  printing `ts`.

### Error taxonomy
- Added `validation`, `database`, `lifecycle`, `runtime`, `transport` — applied
  ONLY to the two over-wide buckets (`config`, `unknown`), and `retryable` is
  computed from the COARSE category, so retry policy cannot move.
- Billing is a **flag** (`billing: true`), not a category: reclassifying
  credit/quota errors would silently change retry behavior. `quota exceeded`
  stays `rate_limit` + retryable + billing.
- No new `sanitizeStreamError` case → user copy unchanged.

### Lifecycle events added (dark zones)
`send.start|stream_end|failed|redirected_to_opencode`, `request_sent|completed|failed`,
`draft.snapshot|materialize_start|materialized|materialize_failed`,
`run.cancel_requested|rejected`, `handoff.start|accepted|failed|not_bound`,
`route.change`, `runtime.mount|unmount`, `boundary_error`, `availability.state.change|recovery`,
`approval.decision.submitted|accepted|failed`, `question.submitted|accepted|failed|dismissed`.
New client-only scope `approval`.

### Gotchas that cost time
- `bun test --path-ignore-patterns "web/e2e/**"` is NOT the project's suite: it
  omits `**/shutdown-lifecycle.test.ts`, which closes the shared SQLite DB and
  cascades into **194** bogus failures ("Cannot use a closed database"). Use the

- Test files share ONE process and ONE `globalThis`: stubbing `fetch` in one

- `new Headers({...})` THROWS on non-ISO-8859-1 values (an emoji in a test

- The logger is a process-wide singleton: a test that changes `bufferSize`/

## Root cause of the twins, fixed at the source

Follow-up: the 80 generated `.js` artifacts were still lying around (a commit
hazard, and the twins would regenerate).

**Root cause:** the ROOT `tsconfig.json` had **no `noEmit` and no `outDir`**, so
a bare `tsc -p tsconfig.json` emitted a `.js` twin beside EVERY source file in
`src/` and `scripts/`. `web/tsconfig.json` already had `noEmit: true`, which is
why `web/` had zero artifacts. Nothing in the repo needs tsc to emit
(`build:backend` = `bun build`, `build:web` = `vite build`, `typecheck` already
passes `--noEmit`, Tauri's `beforeBuildCommand` = `bun run build`).

**Fixes applied:**
1. `tsconfig.json` — added `"noEmit": true`. **Proven:** a bare
   `bunx tsc -p tsconfig.json` now exits 0 and emits nothing (80 → 80 files).
2. Deleted all **80** untracked `.js` artifacts. Verified first that **zero**
   `.js` are tracked by git and **every** untracked `.js` has a `.ts` twin
   (0 exceptions). Backup: `/tmp/tbai-js-artifacts-backup`.
3. `.gitignore` — added `src/**/*.js` and `scripts/**/*.js` as a commit guard.
   Verified `scripts/*.mjs` (hand-written, 5 tracked) is NOT matched.
   Untracked files: **118 → 38**.

**Verification after cleanup:** typecheck 0 · lint 0 (420 files, down from 490)
· build:backend 0 (384 modules / 3.11 MB — unchanged, proving the artifacts were
never part of the build) · build:web 0 (24.2s) · `bun run test` 0
(1343 pass / 2 skip / 0 fail).

**Deliberately NOT done:** no `**/*.test.js` ignore in the test script — that
would silently skip a legitimate JS test in the other direction. `noEmit` +
gitignore removes the cause; a collection guard would only mask a recurrence.

## Stale operationId (live defect) — root-caused from the RUNNING app, then fixed

The app was live on **:3004** with the current build, so the defect was diagnosed
from its own logs instead of guessed at. `curl /api/logs/recent?limit=5000` +
group-by-operationId produced the whole answer.

### Exact root cause
Of 7 sends in the ring, **3 leaked** (`op_5dac6075`, `op_7412072d`,
`op_7e9dedc5`): `send.start` with **no `send.stream_end`**. The last one stayed
"current" for **over an hour**, so the ResizeObserver `window_error` at 15:35:06
and 15:35:33 (route `#/logs`, two different requestIds) inherited it — exactly
the reported symptom.

Mechanism: the finish detector lives in a **per-transport `TransformStream` tap**
(`wrapFetchWithResumable` in `@assistant-ui/ai-sdk`), so it only fires while
THAT transport's body is read to the end. A cancelled/abandoned stream — a Stop,
a route change, a replaced transport (the first send materialises the thread and
swaps transports) — never delivers `finish`, and `endSendOperation` had no other
caller. Sends that ended (marker or `onError`) never leaked; the successful ones
that persisted messages right after `chat_response_closed` did.

### Fix (no architecture change)
1. **Guaranteed release**: every chat-transport response now goes through
   `observeBodySettled`; when the body settles (done / error / **cancel**) the
   operation ends. This is the only signal present on every terminal path.
2. **Id guard**: the settle carries the operationId it was issued under, so a
   superseded response settling late cannot end the operation that replaced it.
3. **Continuations re-open the SAME id** (`attachSendOperation`), so a
   tool/approval turn stays one operation across round trips.
4. **Stack hardening in `operation.ts`**: `end()` no longer restores an
   ALREADY-ENDED enclosing operation — a leaked parent could otherwise be
   resurrected as current and leak its id again.
5. Extracted the lifetime into `web/src/lib/send-operation.ts` so it is testable
   without a DOM.

### ResizeObserver investigation (NOT a TBAi loop)
- TBAi's only write-back observer is `SwapLabel` in
  `components/assistant-ui/elements/surfaces.tsx` — and it is **DEAD CODE**
  (zero usages; only `ShimmerLabel` is used, and it has no observer).
- `reasoning.tsx` / `QuickActions.tsx` observers are chat-surface only, unmounted
  on `/logs`.
- On `/logs` the only mounted observer is **virtua's** (`lib/core/index.js`,
  `new ResizeObserver(e).observe(n)`), used by the log list with a FIXED
  `itemSize={28}` in a fixed-height container. `LogsPanel.onScroll` writes a REF
  (no re-render), so it cannot drive a loop.
- ⇒ No TBAi-authored feedback loop is reachable. Narrow classification is
  therefore justified, and the match is **exact** (not a substring/blanket
  ResizeObserver filter) so a real loop introduced later still errors.
