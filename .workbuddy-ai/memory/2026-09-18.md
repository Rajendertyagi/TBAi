## Code-mode panels are now a FALLBACK, not a history (Phase 1 only)

### Root cause (verified against a real capture, not assumed)

`sse-approve.log:149` (captured 2026-09-17) shows the live server emits
**V1-shaped** `permission.asked` **with** `tool.callID`:

```
{"type":"permission.asked","properties":{"permission":"bash",

```

So a tool-driven permission **does** link to its tool card and renders inline —
`OpenCodePermissions.tsx` already excluded those from the *pending* list. An
earlier theory (that the V2 payload shape caused the duplication) was **wrong**.

The accumulation was caused **only** by the unfiltered resolved map:
`OpenCodePermissions.tsx:178-180` rendered `Object.values(resolved)` with no
filter, and `OpenCodeQuestions.tsx:290-306` did the same for `answered`/`rejected`.

### Change

- `web/src/features/opencode/panelInteractions.ts` — **new**. Pure selector
  `unlinkedPendingPermissions(pending, stale)` (excludes tool-linked + stale) so
  the fate table is assertable without rendering the runtime-bound component.
- `OpenCodePermissions.tsx` — resolved-history block, `ResolvedRow`,
  `ResolvedEntry`, `useOpenCodeThreadState`, `CollapsedDecisionRow`,
  `DecisionBadge` all removed; early return is now
  `if (unlinked.length === 0) return null;`. `useStalePermissionReconcile()` kept.
- `OpenCodeQuestions.tsx` — `answered`/`rejected` blocks, `ResolvedRow`,
  `requestTitle`, `useOpenCodeThreadState`, `CollapsedDecisionRow`,
  `DecisionBadge` all removed; early return is now
  `if (questions.length === 0) return null;`. All pending questions still render
  (the adapter projects no inline question surface, so this is the only
  answerable place).

Fate table — permissions: pending+linked → inline tool card only;
pending+unlinked → `PermissionCard` fallback; resolved+linked → inline collapsed
tool decision only; resolved+unlinked → nothing.

**Why a fallback panel stays:** deleting it outright would make a request with no
tool card unanswerable — that is exactly the "tool hangs at `running` forever"
wedge that was just fixed. Direct chat never hits this because every native
approval is attached to a tool call.

## Code-mode Phase 2 — OpenCode V2 interaction-payload compat (DONE)

**The bug:** the frozen bridge's event switch handles only the V1 names
(`permission.asked`/`replied`, `question.asked`/`replied`/`rejected`). This build
also emits **V2** names, which the adapter has **no case for** → the frame is
dropped **silently**: no error, no card, tool stuck at `running`. A different
failure from the directory-scope one (that at least answered `[]`).

**Shapes PROVEN two ways** — SDK types *and* a real captured frame
(`sse-raw2.log:101`):
```
permission.v2.asked  {id, sessionID, action, resources[], save?, metadata?, source?}
  → the captured frame had NO `source` (a V2 request may have no tool link)
permission.v2.replied {sessionID, requestID, reply}   → field-identical to V1
PermissionV2Source = {type:"tool", messageID, callID}  // `type` required, `source` optional
QuestionV2Info ≡ QuestionInfo, QuestionV2Tool ≡ QuestionTool  → TYPE REMAP ONLY
```

**Mapping** (`web/src/features/opencode/permissionPayloadCompat.ts`, pure,
non-mutating): `action→permission`, `resources→patterns`, `save→always`,
`source→tool` **only when `source.type === "tool"`**, `metadata` defaulted to
`{}`. `patterns`/`always` always emitted as arrays — the card reads `.length` on
both. No `source` ⇒ stays unlinked ⇒ answerable via the Phase 1 fallback panel.
No identity ⇒ frame returned unchanged.

**Wrapper order (load-bearing):** applied **last** in `runtimeClient.ts`, after
hydration. Hydration synthesizes its replayed frames *inside its own wrapper*, so
a normalizer applied earlier would never see them; outermost sees live + replayed
through one mapping.

### Bug my own sanity check caught before hand-off

First version routed **every** `permission.*` frame through the asked-shaped
projection. A reply carries `requestID`, not `id` → failed the identity check →
**passed through unmapped** → the V2 reply would have been dropped. Only
`permission.v2.asked` has differing properties. This is why a 5-minute throwaway
check beats handing off unverified code.

## "No response from AI in Code mode" — diagnosed (NOT my changes)

**The AI IS responding.** Every one of the 6 most recently updated OpenCode
sessions ends with an assistant message whose `time.completed` is set and whose
text is real. So this is a **display/transport** failure, not a model failure.

**Root cause, proven by live call:** `POST /api/opencode/session`
(`{conversationId}`) returns `sessionId` **but `directory: null`** — for every
Code conversation tried. With no directory the browser client cannot scope its
event subscription (`createScopedOpenCodeClient` returns the client unscoped),
so it subscribes to OpenCode's **unscoped `/event` stub**, which carries only
`server.connected` + `server.heartbeat`. No `message.part.updated` ever arrives,
so a finished reply never renders. The app's own code names this field the
explanation: `OpenCodeView.tsx:121-124` — *"`false` means the runtime cannot
scope its subscription and live streaming will not work — the single field that
explains this whole failure mode."*

**Why the directory is null:** the conversation's stored `opencodeSessionId`
(`ses_f4f1e7830ffe0OQztdCWBhmGto`) returns **HTTP 404** from
`GET /session/{id}` — it does not exist on the running server — and the mint
handed back that **same dead id** with a null directory instead of recreating.
`ensureOpenCodeSession` (`src/services/opencode/sessions.ts:185-196`) is written
to recreate on a stale pointer (`fetchOpenCodeSession` returns null on a 404 →
logs `opencode.session_stale` → falls through to create). **That inconsistency
is unresolved** — the observed response matches the stale-pointer branch *not*
having run. Worth checking whether `fetchOpenCodeSession` is actually reached
(and whether `client.session.get` throws on 404 or returns the
`{data, name:"NotFoundError"}` envelope, which has no `id`).

Note: `GET /session/{id}` for a session that DOES exist returns the session
object directly, with `directory: "D:\\Temp\\ai-chat-app"`. So the reader works
when the session is real.

**Not my changes.** Verified independently:
- `permissionPayloadCompat` composition: fake client, same patch order → 5 frames
  in, 5 out, and `permission.v2.asked` correctly became `permission.asked`.
- The app's SSE proxy streams (`server.connected` observed live).
- The app process started 09:41 today, after all my edits, so it runs this code.

**NOT visually verified** — the agent-browser daemon will not start in this

### Fix direction

Do not hand out a live-looking session id with `directory: null`. Either treat an
unreadable directory as stale and recreate (giving a known directory), or fall
back to the conversation's resolved workspace directory — never leave the client
unable to scope. Then a reply renders live instead of only after a reload.

### The follow-up bug: the element was DEAD CODE

Shipped, then the user's screenshot showed the OLD card (`websearch · <query>` +
raw JSON) — proving the element branch never ran. Cause, at `ui.tsx:465`:

```ts
const gated = p.approval != null;   // WRONG
```

**Nearly every tool is gated in this deployment** (the catch-all
`{"permission":"*","action":"ask"}` rule), so `approval` stays non-null for the
WHOLE lifecycle — pending, approved, running, complete. `!gated` was therefore
never true and the element never rendered. **The gate owns the card only while
the decision is PENDING.** Fixed to four conditions mirroring `BackendToolView`'s
own branches:

| Condition | Mirrors |
|---|---|
| `gateUndecided` = `approval != null && approval.approved === undefined` | gate branch (awaiting, or request gone) |
| `awaitingContinuation` = `approved === true && result === undefined && status.type !== "running"` | "Approved — will execute with your next message" |
| `failed` = `status.type === "incomplete"` | cancelled/failed row |
| `denied` = `denialOf(result, approval) != null` | Denied row, via the SHARED exported rule |

`failureOf` is **NOT exported** — don't invent a local copy; `incomplete` covers
it here.

**`useToolArgsStatus` — exact installed signature** (`@assistant-ui/core`'s
`react/model-context/useToolArgsStatus.d.ts`, re-exported by `@assistant-ui/react`):
```ts
type PropFieldStatus = "streaming" | "complete";
{ status: "running"|"complete"|"incomplete"|"requires-action";
  propStatus: Partial<Record<keyof TArgs, PropFieldStatus>> }
```
Two gotchas: `propStatus` is **Partial** (so `undefined` = already complete — only
an explicit `"streaming"` may hold a placeholder), and it **throws outside a
tool-call message part**, so call it unconditionally at the top for stable hook
order.

**Lesson worth keeping:** a guard that reads "does this part have an approval?"
answers a different question from "does the gate own the card?". In a deployment
that gates everything, the first is true forever — so any rich-UI branch behind
it is dead code. Always mirror the shared shell's own branch conditions.

## REUSABLE: vendoring an assistant-ui registry element

Done twice now (web-search, code-diff). The procedure:

1. **Registry URL is `https://r.assistant-ui.com/<name>.json`** — the
   `www.assistant-ui.com/r/...` path 404s. Name is the install id
   (`elements-code-diff`, `elements-web-search`). The JSON gives
   `dependencies`, `registryDependencies` and the file `content` verbatim.
2. **Check `registryDependencies` against the repo** — often
   `elements-surfaces.json`, and `web/src/components/assistant-ui/elements/
   surfaces.tsx` may already export everything needed (it exports `paper`,
   `field`, `mono`, `codeScroll`, `codeSurface`, `ShimmerLabel`).
   `web/src/components/assistant-ui/utils/range.ts` was already vendored too.
   **If a dep is present, don't re-vendor it.**
3. **No `components.json` exists** → vendor by hand; never init one for a single
   element.
4. **Swap palette colours for TBAi tokens** if the element hardcodes
   `emerald`/`red`. The repo's diff tokens are **override hooks with inline
   defaults**, not globals.css entries:
   `var(--diff-add-bg, <fallback>)` + `[--_diff-add-bg:color-mix(…)]`. Same for
   `--diff-add-rule` / `--diff-add-text` / `--diff-del-*`.
5. **Document the deviation** in the vendored file's header — one deviation,
   stated.

**Gotchas that cost time:**
- The web-search page's registration example uses `"use generative"` +
  `externalTool()`, which **throws at runtime in this repo** (no vite plugin).
  The code-diff page's example uses `{ type: "backend", render }` — the pattern
  this repo actually uses. Check per page.
- Registry pages assume `result` is a **structured object**; OpenCode hands us
  **strings**. Always check what our side actually has.
- `CodeDiff` renders the deletion count with **U+2212 `−`**, not a hyphen — which
  breaks a test asserting `toContain("-1")`.

## Tool-block width: the `max-w-md` decision (2026-09-19)

`TerminalBlock` (`terminal-block.tsx:60`) and `CodeDiff` (`code-diff.tsx:97`) both
carry the same official base: `w-full max-w-md overflow-hidden rounded-2xl
font-mono text-xs`. `WebSearch` uses `max-w-sm`. **`max-w-md` = 448px ≈ 58
characters at `text-xs` mono — BELOW the 80-column norm**, so most real diffs and
logs scroll horizontally inside the cap.

`cn` in `web/src/lib/utils.ts` **is** `twMerge(clsx(...))`, so a call-site
`className` genuinely overrides the element's own `max-w-*` ✓ (verified — this is
the thing to check before assuming an override failed).

**Decision (user chose (a)):** removed `className="max-w-none"` from both
`CodeDiff` call sites so diffs match the terminal cards at 448px. Note this is a
**deliberate width reduction** — the legacy `DiffViewer` was `w-full`.

**My stated view, on the record:** the cap is a general-chat default and this is a
*coding* agent, where wide output is the norm. The app is also already
inconsistent — **Reasoning is full width while tool cards are capped**. If diffs
scroll annoyingly, the fix is one rule for ALL machine output (tools + reasoning),
not per-element caps. A middle path is `w-fit max-w-full` (compact when small,
wide when needed; costs ragged widths).

## Permission modes (Manual/Auto) — audit done, plan on disk (2026-09-19)

Plan: **`docs/permission-modes-plan.md`**. Status: audit complete, awaiting ONE
decision before Phase 4.

**Three findings that shape the work:**

1. **`ApprovalCard` / `PermissionGrant` are NOT installed packages** — they are
   **registry elements** (glob `*pproval*` under `@assistant-ui/react@0.15.20`
   returns nothing). Using them = vendoring two more elements by hand. **The TYPES
   are installed** (`@assistant-ui/core@0.3.19`), so they compile against the
   frozen train with no dependency change. Exact shapes + `resolveToolApprovalResponse`
   are recorded in the plan.
2. **The installed contract routes QUESTIONS through the approval seam** —
   `ToolApprovalResponse` has a `{ text }` variant documented as *"Answer to a
   request that asks a question rather than for a decision"*, plus
   `ToolApprovalDisplay = "decision"|"select"|"text"` and
   `toolApprovalAcceptsText()`. This **conflicts with "questions stay separate"**:
   keeping them apart now means *deliberately using a subset* of the contract
   (never `display:"text"`, never `allowFreeform`). Record it as a deliberate
   divergence or someone will "fix" it and break the multi-question protocol.
3. **The official `ApprovalCard` hardcodes three optionIds** (`"once"`,
   `"always"`, `"deny"`) in its docs — NOT the documented kinds
   (`allow-once`/`allow-always`/`reject-once`) and not necessarily any host's ids.
   TBAi's gates come from **OpenCode's** options, so a drop-in cannot work without
   an id-mapping step. Genuine capability gap → document before writing custom code.

**Good news:** `web/src/components/shared/approval-options.ts` **already
implements the official vocabulary faithfully** (`isKnownApprovalOptionKind`,
`approvalOptionApproves`, `approvalOptionLabel`, the four kinds + labels). Only
the *rendering* is TBAi's. Identity is `approval.id` (the library's own doc says
scope semantics belong to the option supplier) — **not toolCallID**.

**The decision that gates Phases 4–5** (put to the user, not guessed):
(i) vendor the elements as **presentational views** and pass callbacks through the
TBAi adapter so the guarded response path stays single — *recommended*; or
(ii) let renderers call `respondToApproval` directly, relaxing the parity guard —
re-opens the failure the guard exists for. **Do not pick (ii) silently.**
