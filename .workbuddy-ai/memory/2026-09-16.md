## OpenCode V1/V2 mismatch hypothesis — DISPROVEN at runtime

Ran the deferred runtime verification. The standing hypothesis ("adapter speaks
V1 `/session/*`, backend speaks V2 `/api/session/*`, so the browser 404 is a
V1/V2 surface split") is **wrong**. Read-only probes; no code changed.

**Environment (measured):** OpenCode binary **1.18.29**; SDK **1.18.31**;
adapter `@assistant-ui/react-opencode` **0.2.23** (npm `latest`); managed server
PID 22396 on **127.0.0.1:52956** (parent = `bun src/index.ts`); TBAi backend on
**0.0.0.0:3000**.

**Measured results (same server, same session):**

| Endpoint | Result |
|---|---|
| `GET /session` (V1 list) | **200**, 31 ids |
| `GET /api/session` (V2 list) | **200**, 50 ids |
| V1-only ids | **0** (V1 ⊆ V2 → one shared store) |
| `GET /session/<id>` | **200** (returns the session object) |
| `GET /api/session/<id>` | **500** `UnknownError` on **13 of 14** sessions |

Every V1 endpoint the adapter calls returns 200. `GET /session/<id>` through the

lifetime (19:40:30→21:19:53, 3373 entries) contains **zero 404s**; only two
non-200s — a `422` and my own probe's `500`.

**Real defects found instead:**

1. **`opencode` log scope is throttled to 1 line/sec** (`logger.ts:444`
   `THROTTLE_BUDGET_PER_SEC = 1`, bucket 100) → **920 lines dropped**. This is
   why the added proxy diagnostics were invisible. Plus `file.enabled=false`, so
   `data/tbai.log` is stale since 2026-09-14.
2. **`readiness.ready` logged `attempts: 9714` in `elapsedMs: 1491`** — the
   probe loop in `waitForHttpReady` busy-spins (connection-refused resolves
   instantly, so the `setTimeout(pollMs)` branch loses the race). Burns CPU and
   floods the logger → feeds defect 1.
3. **`sse.error: TypeError: Invalid state: Controller is already closed` ×12** —
   TBAi's own `observeBody` wrapper in `routes/opencode.ts` calls
   `controller.error()/close()` after the client already cancelled. Diagnostic

   Server-side OpenCode 1.18.29 defect; worth an upstream report.

**Conclusion:** the V1/V2 surface split is real at SDK class level but is **not**
the cause of the observed errors. Do not build a V2 shim. The observed error
spam was (a) `ERR_CONNECTION_REFUSED` = backend simply not running, plus
(b) the defects above.

## OpenCode V2 migration audit — written, no code changed

Wrote `docs/opencode-v2-migration-audit.md`. Audit only; no production code,
`package.json`, lockfile, dependency or OpenCode binary touched.

**Inventory is small.** Backend OpenCode SDK usage is **4 V1 call sites + 5 V2 call
sites**, confined to `src/services/opencode/sessions.ts` and `capabilities.ts`.
`client.ts`, `events.ts`, `permissions.ts` in `src/services/opencode/` are empty
placeholders. The adapter (`@assistant-ui/react-opencode@0.2.23`) has **19 call
sites across 5 namespaces**, all V1.

**Two packages, not one.** The legacy SDK's `client.v2` namespace is NOT the
official V2 API — it is a transitional surface and is incomplete (no `session.remove`,
no `session.fork`, no `session.update`, no `session.diff`, no `session.prompt` text
shape). The official V2 client is **`@opencode/client@2.0.4`** (repo
`anomalyco/opencode`, `packages/client`), a different package with an Effect/Solid
paradigm, typed errors (`SessionNotFoundError` etc.), and deps only
`@opencode/schema` + `@opencode/protocol` (peers `effect`/`solid-js` both **optional**).

**Key transport finding:** `@opencode/client` takes `{baseUrl, fetch?, headers?}`, uses
`/api/*` paths only, and its `event.subscribe` is `sse({method:"GET", path:"/api/event"})`
requiring `text/event-stream`. **The existing TBAi proxy already satisfies all of this
with zero changes.**

**Verdict: C** — the migration needs a contained temporary compatibility layer, with the
qualification that the **backend half is option A** (4 call sites, all with V2
counterparts, can move now without a layer). The frontend half is blocked because
upstream `react-opencode` has no V2 release and `@opencode/client` cannot satisfy the
adapter's `OpencodeClient` interface.

**Blocker: F (combination), D dominant.** 18 of 19 adapter operations need reshaping.
Semantic renames, not just paths: `question`→`session.form`, `abort`→`interrupt`,
`summarize`→`compact`, `revert` splits into `stage`/`clear`/`commit`, `prompt` changes
from `parts[]` to `text`+attachments, permission becomes **session-scoped** with
`reply`→`decision`, `event.subscribe` becomes an **`AsyncIterable`** not an SSE `Response`.
Only `session.status` has no V2 equivalent at all.

**Freeze:** `@assistant-ui/react-opencode` (0.2.23 IS npm `latest` — nothing to upgrade
to), `@opencode-ai/sdk` as its transitive dep, the OpenCode binary.

**Reusable technique** (worth repeating for any library migration): parse the generated
SDK bundle (`dist/v2/gen/sdk.gen.js`) with python regex to dump every
class → method → HTTP verb → URL; and inspect a registry tarball in a temp dir
(`curl <tarball> | tar -xz`) instead of installing it — gives the full `.d.ts` surface
with zero footprint.

## Backend OpenCode V1 → official V2 client, phase 1 — IMPLEMENTED (evening)

**Outcome: 4 of 7 operations migrated; 3 are blocked by the server version, not by TBAi.**

Migrated to `@opencode/client@2.0.4` (all verified live against OpenCode 1.18.29):
`agent.list` → `GET /api/agent`, `model.list` → `GET /api/model`, `session.create` →
`POST /api/session`, `session.get` → `GET /api/session/:id`. All `as unknown as X` casts
AGENTS.md §3 forbids are gone from these paths.

**The decisive finding — the official client is AHEAD of every released server.**
`@opencode/client@2.0.4` targets an OpenCode **2.x** server; the newest release is
**1.18.31** (`anomalyco/opencode`). Proof gathered three independent ways:
1. **Binary route table** (`grep -a -o -E 'C\.(get|post)\("[^"]*","[^"]*"'` on the
   179 MB bun binary): `C.post("session.interrupt","/api/session/:sessionID/interrupt",
   {success:P.NoContent})` → **204**, but the client hard-codes `successStatus: 200` + JSON
   → `ClientError("UnexpectedStatus", 204)`. **Zero `C.delete(...session...)` routes exist**
   → `DELETE /api/session/:id` falls through to the SPA handler (200 + `text/html`), the
   client expects 204 → `UnexpectedStatus(200)` and **nothing is deleted** (session still
   resolved afterwards). No `"server.status"` route either → `/api/status` is absent.
2. **Live probes**: `/api/status` → 200 `text/html` on all three running instances;
   `/api/health` → 200 `{"healthy":true}`; `/api/agent` + `/api/model` → 200 JSON.
3. **SDK cross-check**: `@opencode-ai/sdk@1.18.31`'s V2 `Session3` has `interrupt` but
   **no `remove`/`delete`**, and never mentions `api/status`.

**Deliberate non-migration (not a gap in the work — a ruled-out option).** No `fetch`-shim
bridge was built. Bridging `session.interrupt` would require fabricating an
`{interrupted:boolean}` body the server never sends — exactly the "incorrect semantic API"
the spec's §6 rules out. Instead the two calls stay on the V1 routes, isolated in ONE
function `callV1SessionRoute` (best-effort, never throws) with the removal condition
documented inline.

**Readiness (§6):** `/session/status` (V1) → `/api/health` (V2, present, semantically
correct). The official mechanism `server.status()` → `/api/status` is unusable.

**New `src/services/opencode/errors.ts`.** The client throws TWO shapes and both must be
handled: `ClientError` (transport / undeclared status / non-JSON, discriminated by
`.reason`) **and plain objects, not Errors**, for contract-declared statuses — e.g.
`{_tag:"SessionNotFoundError", sessionID, message}` on a 404. Use the package's own type
guards (`isSessionNotFoundError`, `isUnauthorizedError`, `isForbiddenError`,
`isInvalidRequestError`, `isServiceUnavailableError`) — 33 exports total. Mapped to one
`OpenCodeError{kind, statusCode, code:"OPENCODE_ERROR"}`, shaped so the existing shared
`classifyError` funnel reads it with no OpenCode-specific logging path.

**Runtime/type divergence to remember:** the official `AgentInfo` declares `name: string`
but the 1.18.x server returns **only `id`** (item keys: `id,request,system,description,
mode,hidden,permissions`). Agent `name` therefore falls back to `id`. `ModelInfo` declares
`modelID` which the server also omits (unused by us). Also: **all 36 live models currently
declare `variants: []`**, so the thinking chip is hidden for every model right now.

**Verified:** typecheck exit 0 (backend+web), build exit 0, `bun run test` **572 pass /
2 skip / 0 fail**, live cold-start (spawned + probed ready in **1888 ms**, `/api/health`
200, capabilities 7 agents + 36 models, V1 abort/delete → 200 then 404 as
`session_not_found`). Bundle: `@opencode-ai+sdk` **0 refs** in `dist/index.js`,
`@opencode+client` 6 refs → legacy SDK fully out of the backend.

**Gotcha that cost time:** shell-escaping Windows paths into a JSON body produced
`SyntaxError: Invalid escape character T` and `Path is not absolute: D:` — server-side 500s
that looked like an API rejection. **Serialize JSON with the runtime (`JSON.stringify`),
never by hand in bash/heredoc.** The server log at
`~/.local/share/opencode/log/opencode.log` is the fastest way to see the real error.

**Also note:** `bun test` bare ≠ `bun run test` — the script carries
`--path-ignore-patterns "web/e2e/**"`. Bare `bun test` picks up Playwright specs and
reports 10 bogus failures.

**Still open by instruction (do NOT fix without being asked):** readiness busy-spin
(measured again: 5780 probes in 1000 ms), throttled `opencode` log scope, `sse.error`
controller-already-closed, `GET /api/session/{id}` 500s on ~93% of sessions.

## Backend V2 migration — Step 4 resolved: adaptive transport bridge (2026-09-16, late)

**Supersedes the earlier "no bridge was built" conclusion.** The user's Step 4 explicitly
required `session.interrupt` → `session.remove` to be real V2 calls ("do NOT simply rename
methods and ignore the changed response contract"). Both are now genuine official-client
calls; the wire-level compromise moved one layer down into **one** function, `compatFetch`
in `src/services/opencode/client.ts`:

- interrupt: pass through; only if the server answers **204** report it to the client as the
  `200 + {"interrupted":true}` its own contract declares.
- remove: issue V2 `DELETE /api/session/:id` **first**; only if it returns the SPA fallback
  (200 + `text/html`) retry the legacy `/session/:id`, reporting 204.

Both are **adaptive** → inert on an OpenCode 2.x server, deletable then. Net win: the old
`callV1SessionRoute` approach left `session.remove` throwing and being swallowed, i.e. it
silently deleted nothing.

**Live wire log proves it** (8 backend SDK calls in one cold-start run):
`/api/agent`, `/api/model`, `GET /api/session/:id`, `POST /api/session/:id/interrupt` (204),
`DELETE /api/session/:id` (`v2-missing`), `DELETE /session/:id` (`v1-fallback`), `/api/model`,
`POST /api/session`. **7 of 8 V2**, plus exactly the one documented exception.

## Added: `recordTransport` runtime trace

The OpenCode server logs **no HTTP requests of its own** (`~/.local/share/opencode/log/opencode.log`
only carries lifecycle messages). That made "verify backend requests use V2 paths" impossible.
`recordTransport` in `client.ts` now emits one `opencode.transport` debug line per SDK call
(`method`, `pathname`, `status`, `via`) — `via` ∈ `v2 | v2-missing | v1-fallback`. Method/path/
status only, never query strings/bodies/headers. This is what makes the V2-only invariant
verifiable at runtime, not just statically.

## FIXED (was "open by instruction"): readiness busy-spin

Verifying the new readiness endpoint exposed that the loop raced the probe against its own
`setTimeout(pollMs)` and, on a fast negative probe (connection refused = the whole cold-start
window), re-probed immediately. Measured **9,070 attempts in ~2.8 s**. Worse than CPU burn:
the logger's per-scope bucket (burst 100, refill 1/s) was exhausted instantly, silencing the
entire `opencode` scope for ~100 s and **dropping `readiness.ready` and `opencode.spawn`
themselves** — the two lines that prove readiness worked.

Fix: await the interval the probe raced against (resolves at once if already elapsed, so a
slow probe is never double-delayed). After: **5–6 attempts in ~1.0–1.25 s**, and the success
lines are logged. Gate unchanged — the HTTP probe is still the only readiness authority.
This is not scope creep: the function's own doc comment already promised "short `pollMs`
intervals" and the code wasn't delivering them.

## Phase B — OpenCode live-reply bug: root cause + permanent fix (2026-09-16, late)

**Symptom:** in Code mode an AI reply was not visible live; it took **two** page refreshes to
appear. Pre-existing — **not** caused by the phase-1 V2 migration.

**Root cause (proven by A/B `curl` in the same time window):** OpenCode keys `/event` on a
**directory**. `GET /event` (no param) is a **stub** — only `server.connected` +
`server.heartbeat`, no session events, ever. `GET /event?directory=<session dir>` returns the
real stream (`session.updated`, `message.updated`, `message.part.updated`,
`message.part.delta`, `session.status`, `session.diff`, `text`) in the V1 `{type, properties}`
envelope the frozen library already normalizes. The frozen
`@assistant-ui/react-opencode@0.2.23` calls `client.event.subscribe(undefined, …)` — unscoped —
so the browser held a healthy reconnecting stream carrying **zero** events (measured: 91 s
connected, 1 `server.connected` + 9 heartbeats, 0 session events during a live generation).
The reply was persisted all along; the runtime's self-heal (`stream.reconnected` → `refresh()`)
never fires because a stub stream never drops. Each manual refresh was the only thing that ever
advanced state → refresh #1 got a mid-flight snapshot, refresh #2 got more.

**Fix (failing boundary only, no forbidden masks, no second runtime, no library patch):**
- `ensureOpenCodeSession` now returns `OpenCodeSessionBinding` = `{ sessionId, directory }`,
  reading the directory from the **server's own session record** — `location.directory` (V2
  shape) with top-level `directory` fallback (1.18.x V1 wire) — NOT re-derived from the folder
  table, so it survives a workspace migration. Liveness refactored into
  `fetchOpenCodeSession`; `isOpenCodeSessionLive` kept as a thin predicate (all 8 existing
  liveness tests unchanged).
- `POST /api/opencode/session` returns `{ sessionId, directory }`.
- New `web/src/features/opencode/eventScope.ts` → `createScopedOpenCodeClient(baseUrl, directory)`
  overrides **only** `client.event.subscribe` to merge `directory` in. Same single subscription,
  same lifecycle. Every other request byte-identical (scoping the whole client via the SDK's
  `directory` option was rejected — its interceptor would also rewrite history/permission calls).
  `directory: null` → unscoped client (previous behaviour), never a guessed path.
- `directory` is a **documented** param of that route in the OpenCode V2 SDK → supported, not a workaround.
- Frontend runtime client is `useMemo`'d on the scope alone (the library keys its controller
  registry on client identity — a per-render client would churn the subscription).

**Verified:** typecheck clean; 604 pass / 2 skip / 0 fail; live warm-browser run —
send → live in 38.4 s **with no refresh**, second send → live in 31.2 s, refresh #1 and #2
change **nothing** (3 assistant bubbles before and after both), 3/3 event requests scoped
(`directory=`), 0 unscoped. Regression test `web/src/features/opencode/liveStream.test.ts`
drives the real `OpenCodeEventSource` + `OpenCodeThreadController` + projection against a fake
server reproducing the stub/scoped split, asserting the streamed reply reaches thread state with
**no history load**; **mutation-checked** (disabling the scope fails it at the boundary).

- **Assert on ASSISTANT bubbles only** (`[data-message-id]` with class containing `items-start`) —

## Permission wedge fixed: a forgotten request is retired (Phase 1)

**Symptom:** `Permission request not found: per_0ab678311001IYqH2yLUhx8hT3` on BOTH Approve and Deny →
card cannot be dismissed; also rendered twice (nested in the tool block + above the message).

**Root cause (verified live, not inferred):** OpenCode keeps pending permissions in **server memory
only**, sessions persist to disk. `GET /api/opencode/permission` → `[]` while `session.get` → 200; the
port-3300 scratch instance was a *different* managed server (spawn port 55282) that resolved the
session but held no permissions. The frozen adapter (0.2.23) has **no way to clear it**:
`handleStreamReconnect` (`OpenCodeThreadController.ts:431-479`) is **add-only** (skips ids already
pending, never removes forgotten ones) and runs from exactly one line (`:423`); `refresh()`/`load()`
dispatch only `history.loading`/`history.loaded` and never touch permissions. Stuck by construction.

**Fix — three parts, all ours:**
1. `OpenCodePermissions.tsx` renders only requests with **no tool call** (`!req.tool?.callID`) — the
   officially documented scope. Tool-linked permissions belong to the in-message
   `ToolFallbackApproval` (projected as `{id, options}`, `openCodeMessageProjection.js:174`).
   Removes the duplicate + the nesting in one line.
2. `stores/stalePermissionsStore.ts` (new) + `features/opencode/stalePermissions.ts` (new): reconcile
   the adapter's `pending` against `/api/opencode/permission` and mark the difference. Re-checks every
   **5 s while any request is outstanding** (a restart mid-request orphans an ALREADY-pending request,
   and nothing else re-triggers a reconcile). Stops when the set empties.
3. `elements/tool-fallback.tsx` returns null for an approval whose id is in the set (presentation only);
   `isPermissionGone` failure marks the id as a backstop. Transient failures stay retryable.

**Why the probe is sound:** `/api/opencode/permission` is NOT a hand-written route — it falls through
the catch-all proxy (`src/routes/opencode.ts:127`) to `openCodeServerManager.ensureBaseUrl()`, the SAME
instance the runtime talks to. So a live permission is never wrongly marked (no regression) and an
orphaned one always is. **This was the highest-risk assumption and it was checked.**

**Layering:** matcher lives beside the set in the store so the kit imports `@/stores/*`, never a feature
module. `ChatWindow.tsx` deliberately UNTOUCHED (keeps its "assistant-ui-primitives-only" contract — an
earlier draft imported the store there and was reverted).

**Verified:** typecheck exit 0; **111 web tests pass / 0 fail**; bundle built non-destructively and
artifact-diffed — `permission request not found` 0→1, `markStale` 0→2, guard folded into the bail-out
chain as `s!=null&&R.has(s.id)`, poll as `const oFe=5e3`.
**NOT verified:** no browser reproduction — staging it needs a permission orphaned while pending
(restart the managed server mid-request), which was not done.

**Reusable gotchas:**
- The matcher test caught a real gap before shipping: a non-`Error` throwable carrying `.message` was
  missed. Missing the signal IS the wedge, so it now reads `.message` off any object.
- Minified bundles fold consecutive `if (…) return null` into one `||` chain, so **regex-grepping the
  built bundle for a guard can fail even when the code shipped**. Verify via a stable marker (store
  property names like `markStale` survive minification) or by count-diffing against the previous bundle.
- `bun run test` in the full suite shows 4 timeouts in `runBash`/`run_command`/`lists processes`
  (backend tests that spawn real processes) — **pre-existing load flakiness**, not caused by web
  changes; the same test passes at 2.6 s alone. Don't chase these.
- There is **no** `/api/opencode/*` route table entry for anything but `/session`, `/session/terminate`,
  `/capabilities`; everything else is the `app.all("*")` proxy. Check `src/routes/opencode.ts:127`
  before assuming an endpoint is missing.
